# H4: peer prefix lookup-and-pin

Run it with `uv run ms run -f examples/kv-transfer/h4.yaml --detach`. The probe
is `src/modelsight/probes/kv_peer_lookup.py`.

## Hypothesis

With vLLM's peer lookup-and-pin branch (`NixlConnector`, pull mode), engine B
can take a cached prompt prefix from engine A's KV cache by block hash. One
request goes to B, and A computes nothing. Specifically:

1. **A computes nothing.** B sends the prompt's block hashes to A over the NIXL
   side channel. A pins the blocks it already holds and replies with their ids,
   without scheduling a prefill.
2. **B loads the right KV.** B pulls exactly the prefix A held and computes only
   the rest. Its greedy output then matches what B produces when it computes
   the whole prompt itself.
3. **Misses fall back cleanly.** When A holds nothing, B computes the whole
   prompt and pulls nothing.
4. **Pins don't leak.** Every pin A takes for B is released once B's read is
   done.
5. **Latency.** For a cached prefix, B's time to first token (TTFT) on the peer
   path is no worse than today's flow, where A prefills and B pulls. It is lower
   than B recomputing the prompt.

## Experiment

### What's tested

Each session gives one pair of consecutive agent turns, `previous` and
`current`. `current` extends `previous`, the way an agent's context grows. Each
case starts from fresh prefix caches on both engines: before every arm, the
probe resets both caches and then warms A with the case's prefix.

| Case | A holds before the request | B should pull | B should compute |
|---|---|---|---|
| `full` | the whole `current` prompt | every full block of `current` | the tail after the last full block |
| `partial` | the `previous` prompt | the full blocks shared with `previous` | the new turn's tokens |
| `miss` | nothing | nothing | the whole prompt |

Each case runs these arms against B:

| Arm | Flow |
|---|---|
| `peer` | One request to B with `peer_lookup` and A's address. B asks A by block hash, A pins and replies, and B pulls and computes the rest. |
| `stock` | Today's disaggregated flow: a prefill request to A, then B pulls A's blocks and decodes. Not run for `miss`. |
| `recompute` | B computes the whole prompt itself. This is the reference output. |

### Checks and expected outcomes

A failed check fails the run.

| Check | Expected outcome | How it's measured |
|---|---|---|
| `served` | A serves 0 requests during every peer arm. | Change in A's `vllm:request_success_total`. |
| `lookup` | A's log shows a lookup during every peer arm. | `lookup_pin` lines in A's log; the lookup modules log at DEBUG. |
| `pulled` | B's NIXL bytes match the prefix A held, within 10%. 0 on a miss. | B's NIXL transfer metrics, against bytes per token calibrated from the stock arm. |
| `equivalent` | At least 95% of pulled arms match B's recompute token for token. | Greedy decode of 16 tokens, compared exactly. |
| `no_leaks` | A can reset its prefix cache at the end. | `/reset_prefix_cache` on A; vLLM refuses it while any block is held. |

The expected B TTFT ordering:

- `full`: peer ≤ stock < recompute.
- `partial`: peer ≤ stock < recompute.
- `miss`: peer ≈ recompute, plus one side-channel round trip (milliseconds).

### Inputs

| Input | Value |
|---|---|
| Hardware | Modal, one container, 2 × A100-80GB |
| GPU per engine | A on GPU 0, B on GPU 1 |
| Model | Qwen/Qwen3-8B (full attention, 8 KV heads) |
| Engine | vLLM, built from `usationlabs/vllm` branch `feat/nixl-peer-lookup-pin` with `VLLM_USE_PRECOMPILED=1` |
| KV transfer | NIXL 1.5.2, `NixlConnector`, `kv_role: kv_both` on both engines, `kv_load_failure_policy: fail` |
| Peer lookup | `kv_connector_extra_config: {"peer_lookup": true}` on both engines. Defaults: pins capped at 25% of A's pool, 5% of the pool kept free, 2 s lookup timeout on B, 30 s lease |
| Parallelism | None: TP=1, PP=1, DP=1, DCP=1 on each engine |
| Ranks / workers | 1 worker (rank 0) per engine, 2 in total |
| Block size | 64 tokens: vLLM's choice for this model and GPU, seen in the logs (27,712 tokens pinned as 433 blocks). The probe's `--block-size 16` only sets its own expected-hit estimate, which lands within one 64-token block |
| Prefix hashing | sha256 (`--prefix-caching-hash-algo sha256`), so hashes match across processes |
| Max model length | 32,768 tokens |
| GPU memory utilization | 0.9 per engine |
| KV cache allocation | `--no-enable-extensible-kv-cache` on both engines |
| UCX logging | `UCX_PROTO_INFO=y`, so B's log names the transport its reads take |
| Scheduling | vLLM defaults, including async scheduling |
| Prompts | Turns of real agent sessions from `nebius/SWE-agent-trajectories`, rendered with the model's chat template, up to 30,000 tokens |
| Request count | Up to 20 sessions × 3 cases (a session without a usable turn pair is skipped). Counting warm-ups on A and the stock prefill, `full` and `partial` send 7 requests each and `miss` sends 2, so up to 320 in total |
| Concurrency | 1: one request in flight at a time |
| Output | 16 tokens per request, greedy |
| Seed | 0 |

### Load

The run doesn't saturate the CPU or GPU, by design. Requests run one at a
time, so each engine has at most one sequence running, and the GPUs sit idle
between requests. The run tests correctness and single-request latency, not
throughput or behaviour under load.

### Not covered

These are left for later experiments:

- Concurrent load, pin pressure and the pin cap.
- TP>1 or a mismatch in TP between A and B.
- A router that picks the peer from KV events, including a stale index after
  A evicts.
- Lease expiry and heartbeats over long waits.
- Hybrid or Mamba models, which A refuses.

## Results

The run is `results/h4-20261108-121848`. Times are B's median TTFT in
seconds, over 20 sessions.

### Latency and checks

60 records, 0 errors, and every check passes.

| Case | recompute | stock | peer |
|---|---:|---:|---:|
| `full` | 1.291 | 0.065 | 0.530 |
| `partial` | 1.305 | 0.069 | 0.595 |
| `miss` | 1.285 | – | 1.609 |

| Check | Result |
|---|---|
| `served` | PASS: A served 0 requests during every peer arm |
| `lookup` | PASS: 40 `lookup_pin pinned` and 20 `lookup_pin missed` on A, one per peer arm |
| `pulled` | PASS: B's bytes matched the held prefix (147,822 bytes per token) |
| `equivalent` | PASS: 96 of 100 pulled arms matched recompute. The 4 that differ include a stock arm, so they're not specific to the peer path |
| `no_leaks` | PASS: A reset its prefix cache at the end |

Both pulled arms copy over UCX `cuda_ipc` (GPU to GPU), and the copy takes
16–35 ms per pull in B's log.

### Where the peer arm's time goes

B's and A's logs, session 0 `full` (27,712-token hit),
against the stock arm of the same session:

| Step | stock | peer |
|---|---:|---:|
| B sends the lookup → A pins | – | 37 ms |
| A pins → B acts on the reply | – | 254 ms |
| B has the hit → `start_load_kv` | 1 ms | 377 ms |
| `start_load_kv` → KV received | 16 ms | 18 ms |
| KV received → request finished | ~210 ms | 625 ms |

Session 5 (a 9,152-token hit) had the same three waits at 66, 154 and 312 ms.

## Interpretation

1. **A computes nothing (hypothesis 1 holds).** A served no request during any
   peer arm. It only pinned blocks and answered the lookup.

2. **B loads the right KV (hypothesis 2 holds).** B's pulled bytes matched the
   prefix A held, and 96 of 100 pulled arms matched recompute token for token.
   The 4 that differ include a stock arm, so they are not caused by the peer
   path.

3. **Misses fall back cleanly (hypothesis 3 holds).** On every miss, B pulled
   nothing and computed the whole prompt.

4. **Pins don't leak (hypothesis 4 holds).** A reset its prefix cache at the
   end, so it held no pins.

5. **Latency (hypothesis 5 partly holds).** Peer beats recompute: B's TTFT drops
   from about 1.3 s to about 0.55 s on a cached prefix. It does not match
   stock (0.065 s), and a miss costs about 0.3 s more than recompute instead of
   a few milliseconds. The copy is not the cause; it takes 16–35 ms on both
   paths. The extra time is B's scheduler not revisiting the request while
   the lookup is out (`get_num_new_matched_tokens` returns `None` and
   `skip_request` in `vllm/v1/core/sched/scheduler.py` skips it), and again
   before the load starts. B is not idle during these waits. Removing them
   should bring peer close to stock.

These results are for one request at a time on two idle GPUs in one machine.
