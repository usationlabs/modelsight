# H5: peer lookup-and-pin with A busy

H4 measured peer lookup-and-pin on an idle A, which is the one case where a
router would just send the request to A. H5 asks the question that matters in
practice: when A is busy serving other agents and also holds a prefix that a
new request needs, should B pull it from A by lookup (peer), or should A
prefill it first and hand B the blocks (stock)?

## Hypothesis

1. **Peer is no slower than stock under load.** At every load level, peer's
   end-to-end TTFT is no worse than stock's. Stock's prefill request has to
   enter A's queue and wait for a step slot. Peer's lookup does not enter the
   queue: A serves it inside its next scheduler step and the reply ships once
   that step has been processed, so within one or two of A's steps.
2. **The gap grows with A's load.** As A gets busier, stock's TTFT rises with
   A's queue wait and step time, while peer's rises only by one or two A steps
   (the lookup reply) plus any slowdown of the pull.
3. **Correctness holds under load.** The pulled bytes match the prefix A held,
   B's output after a pull matches its recompute, A serves no request for a
   peer arm, and no pin leaks.

## Experiment

### Load on A

AIPerf generates the load, one AIPerf run per load level. The probe starts it,
measures while it runs, and stops it:

1. Start `aiperf profile` against A (chat endpoint, streaming) with
   `--concurrency N`, `--concurrency-ramp-duration 20` (so A is not hit by a
   burst), `--custom-dataset-type multi_turn --input-file background-N.jsonl`,
   `--osl 256` with `ignore_eos`, and a `--benchmark-duration` longer than the
   level needs. Each level writes to its own artifacts folder.
2. Wait for the ramp plus about 10 s, until A's `vllm:num_requests_running`
   reaches about N.
3. Run the measured cases, sampling A's running and waiting counts during each
   arm.
4. Stop AIPerf with one SIGINT, which makes it cancel its requests and write
   its summary (a second SIGINT could lose it), wait for A to drain, reset both
   caches while A is idle, and go to the next level.


`background-N.jsonl` holds agent sessions from the same traces
(`nebius/SWE-agent-trajectories`) but different sessions from the measured
ones. Each turn holds only the user's new text (the system prompt rides on the
first). AIPerf sends the history with every turn: the earlier user turns and
the model's own 256-token replies, so A reuses cached KV the way agent traffic
does and sees a mix of partial prefills and decodes. The trace's own assistant
turns are not replayed. The
load shares nothing with the measured requests: every measured arm uses its own
`cache_salt`, which changes every block hash from the first block on.

- The load is capped at about 128k tokens in flight on A, so it can't evict the
  measured prefix (A's cache holds about 380k tokens). Each background prompt
  is limited to min(128k / N, 32k) tokens, the 32k being the engine's
  `max_model_len`. The limit applies to the cumulative prompt of every turn
  (the system prompt, the user turns so far and 256 tokens per earlier reply):
  a session stops at its last turn that fits. AIPerf repeats sessions when it
  runs out, so the probe loads a pool of 300 sessions and warns when a level has
  fewer background sessions than N. So at N = 1 and 2 the load is at most 32k and 64k tokens, not 128k;
  the levels do not scale the token load evenly, and the results say so.
- The levels are a sweep: N = 0, 1, 2, 4, 8, 16, 32. N = 0 runs no AIPerf and
  is H4.
- AIPerf's own TTFT, inter-token latency and throughput for A are kept per
  level, next to the probe's samples of A's running and waiting requests, so
  each level's real load is known.

B carries no other load, so only A's load changes.

### No cache resets under load

vLLM refuses to reset a prefix cache while requests hold blocks, so H4's
"reset before every arm" can't run while the load is on. Instead, every arm uses
its own `cache_salt`. The salt changes every block hash, so each arm starts
with nothing cached on either engine, and nothing it caches can affect another
arm. A is warmed with the case's prefix under that arm's salt, and the measured
request uses the same salt. A's prefix cache is reset once, at the end, after
the load stops, as the leak check.

### Cases and arms

The cases are H4's: `full`, `partial` and `miss`.

| Arm | Flow | Clock |
|---|---|---|
| `recompute` | B computes the whole prompt. The reference output. | B's request |
| `stock` | A prefill request to busy A, then B pulls A's blocks. Not run for `miss`. | From the prefill request to A until B's first token |
| `peer` | One request to B. B asks A by hash, A pins at its next step and replies, B pulls. | B's request, which includes the lookup |


### Checks and expected outcomes

A failed check fails the run.

| Check | Expected outcome | How it's measured |
|---|---|---|
| `served` | A serves no request for a peer arm. | Peer requests carry a recognizable request id (the `X-Request-Id` header); A's log must show no finished request with that id. If vLLM rewrites ids, `served` is checked at N = 0 only, as in H4 |
| `lookup` | A's log shows a lookup during every peer arm. | `lookup_pin` lines in A's log |
| `pulled` | B's bytes match the prefix A held, within 10%, and 0 on a miss. | B's NIXL metrics. An arm whose own prefix A evicted (a peer miss or short pull on `full` or `partial`) is counted as an eviction and reported, not failed. A's overall eviction counter is not used: without resets, the arms' stale salted copies are evicted all the time |
| `equivalent` | At least 95% of pulled arms match B's recompute over 16 greedy tokens. | As in H4 |
| `no_leaks` | A can reset its prefix cache once the load stops. | `/reset_prefix_cache` on A |

The expected end-to-end TTFT for `full` and `partial`:

- N = 0: peer ≈ stock, both well below recompute.
- N > 0: peer ≤ stock, with the gap widening as N grows.

For `miss`, peer ≈ recompute plus the lookup round trip, which grows by about
one A step under load.

### Inputs

As in H4 (two A100-80GB on Modal, Qwen/Qwen3-8B, vLLM `feat/nixl-peer-lookup-pin`,
`--no-enable-extensible-kv-cache`, block size 64), with these changes:

| Input | Value |
|---|---|
| Sessions per level | 10 measured sessions × 3 cases |
| Load levels | N = 0, 1, 2, 4, 8, 16, 32 background sessions on A |
| Load size | at most about 128k tokens in flight on A (32k at N = 1, 64k at N = 2); 256 output tokens per turn |
| Run time | about 7 × half of H4, plus about a minute per level for AIPerf's ramp, the settle wait and the drain, so roughly 80–90 min on 2 × A100. The run timeout goes up to 150 min |
| Load generator | AIPerf, installed in the image by `ms` (flags checked against 0.13.0); the version is saved in `env.txt` |
| Logging | DEBUG timing as in H4, without the per-request hash list |
